# Frame Pacing Loop Strategies — Application-Level Levers on a Fixed 60 Hz Panel

**Question answered:** what do published game-engine, graphics-engineering and first-party platform sources actually say about structuring a macOS game loop to hold a 60 fps median on a fixed 60.00 Hz display — fixed timestep with render interpolation, uncapped render plus an explicit limiter, and display-link-driven pacing — and can any application-level strategy close a ~12 microsecond median gap that a VSync-locked loop already shows?

Scope note: this file owns the *loop* (when a frame starts, how the simulation clock is advanced, which clock the loop is slaved to). Swapchain and present-path knobs (`PresentMode`, `desired_maximum_frame_latency`, `CAMetalLayer` properties) are covered by the sibling present-path research file and appear here only where they constrain what a loop can do.

**Method.** Search order actually used: (1) `context-awesome` (`find_awesome_section` for "game loop", `search_awesome_items` for "frame pacing") to locate curated lists on the topic; (2) `gh_grep searchGitHub` for real call sites of the exact APIs — `desired_maximum_frame_latency`, `mach_wait_until`, `maximumDrawableCount`, `displaySyncEnabled`, `CVDisplayLinkCreateWithActiveCGDisplays`, `presentDrawable`, `pub fn request_redraw`, `present_drawable`; (3) `web_search` restricted to owning domains (`developer.apple.com`, `docs.rs`, `registry.khronos.org`, `github.com/gfx-rs/wgpu`, `github.com/rust-windowing/winit`, `docs.unity3d.com`, `docs.godotengine.org`, `dev.epicgames.com`, `amd.com`), with Stack Overflow / Reddit / forum material admissible only as labelled [ANECDOTE]; (4) local primary artifacts: Apple SDK headers (`MacOSX.sdk` 26.5) and the vendored crate sources for the pinned versions (`winit-0.30.13` under `~/.cargo/registry/src/`, `wgpu` / `wgpu-hal` v25.0.0). **Negative result from step 1:** the curated awesome-list corpus has no macOS, Metal, wgpu, game-loop or frame-pacing list — `find_awesome_section` returned only generic "game" categories (`learn-anything/games`, `gmh5225/awesome-game-security`, `killop/anything_about_game`) and `search_awesome_items("frame pacing")` matched frame-making/design tools (`davidfurlong/awesome-frames`, `podo/awesome-framer`, `open-frames/awesome-open-frames`), none of which owns a frame-pacing source. Step 3 was therefore the only route to the owning documentation. No arxiv paper was used: no claim in this file rests on a quantitative human-perception or latency study.

## The question

Target: median (p50) frame interval $\le 16.667\ \text{ms}$, i.e. p50 $\ge 60.0$ fps, on a fixed 60.00 Hz panel (author's machine: Apple M5, built-in Liquid Retina 1710×1112 at 60.0 Hz, `NSScreen.maximumFramesPerSecond` = 60).

Measured starting point (600 frames per run, temporary probe since reverted):

| Run | mean | p50 | p95 | p99 | max | sim | draw+present |
|---|---|---|---|---|---|---|---|
| speed x0 | 16.602 | **16.658** | 17.084 | 17.320 | 19.640 | 0.001 | 16.544 |
| speed x100 | 16.630 | **16.679** | 17.132 | 18.377 | 40.182 | 0.123 | 16.428 |
| speed unbounded | 16.625 | **16.664** | 17.122 | 17.435 | 32.528 | 1.579 | 14.974 |

All values in milliseconds. One panel period at 60.00 Hz is $1/60 = 16.6667\ \text{ms}$, so the target is not "render faster than the panel": it is "make the median interval exactly one panel period". At x100 the p50 sits **+12.3 µs** above the period; at x0 it sits **−8.7 µs** below it. The loop is already bracketing the target from both sides, which is why every mechanism below is judged on whether it moves the *phase* of the frame start relative to vsync, not on throughput.

## Findings

### Part A — Mechanism findings

**A1. [PRIMARY] On a fixed-refresh display, presentation is quantized to the panel period; a frame that misses its slot waits a whole extra period.**

Apple's own statement of the mechanism, WWDC21 session 10147 *Optimize for variable refresh rate displays*: "Most displays on Apple systems work at fixed refresh rates. That is, they refresh themselves at a consistent rate whenever they are powered on." and, describing the 60 Hz diagram, "Each frame is presented to the display, where it stays for 16ms before the display is refreshed. If there's a new frame drawn by your Mac ready in the Framebuffer, then that new frame is presented. Otherwise, the previous frame is shown again." The session then quantifies the penalty: a frame that lands 9 ms after the previous frame was first displayed is displayed for the full 16 ms slot "instead of the 8ms you intended. This results in a perceptible hitch in your app." (Apple, WWDC21 10147, transcript.)

The same quantization is normative at the graphics-API level for the present mode this app uses. Vulkan specification, `VK_PRESENT_MODE_FIFO_KHR`: "specifies that the presentation engine waits for the next vertical blanking period to update the current image. Tearing **cannot** be observed. An internal queue is used to hold pending presentation requests. New requests are appended to the end of the queue, and one request is removed from the beginning of the queue and processed during each vertical blanking period in which the queue is non-empty." (Khronos, `VkPresentModeKHR`.) wgpu's `PresentMode::Fifo` is the same contract: "Every vertical blanking period, the presentation engine will pop a frame off the queue to display. If there is no frame to display, it will present the same frame again until the next vblank." (docs.rs, `wgpu::PresentMode::Fifo`, wgpu 25.0.0.)

Panel rate symbols: `NSScreen.maximumFramesPerSecond` — "The maximum number of frames per second that the screen supports."; `NSScreen.maximumRefreshInterval` — "The largest refresh interval that the screen supports. … corresponds to the lowest refresh rate of the display."; `CGDisplayMode.refreshRate` — `var refreshRate: Double { get }`.

Consequence for the target: the *presentation* cadence cannot be made shorter than one period. What an application can still move is the **distribution of its own wake-up time** relative to the vblank boundary — i.e. whether the median interval lands on exactly one period or oscillates across a period boundary. That is the entire remaining problem.

**A2. [PRIMARY] The canonical fixed-timestep-with-interpolation pattern, stated exactly.**

Source: Glenn Fiedler, *Fix Your Timestep!*, Gaffer On Games (the article the entire industry cites for this pattern). The final algorithm, verbatim from the article:

```c
double t = 0.0;
double dt = 0.01;

double currentTime = hires_time_in_seconds();
double accumulator = 0.0;

State previous;
State current;

while ( !quit )
{
    double newTime = time();
    double frameTime = newTime - currentTime;
    if ( frameTime > 0.25 )
        frameTime = 0.25;
    currentTime = newTime;

    accumulator += frameTime;

    while ( accumulator >= dt )
    {
        previousState = currentState;
        integrate( currentState, t, dt );
        t += dt;
        accumulator -= dt;
    }

    const double alpha = accumulator / dt;

    State state = currentState * alpha +
        previousState * ( 1.0 - alpha );

    render( state );
}
```

The article's own statement of why the accumulator exists: "the renderer **produces time** and the simulation **consumes** it in discrete dt sized steps", and of why interpolation exists: with a plain accumulator "we're displaying the state of the physics simulation at a time slightly different from the render time, causing a subtle but visually unpleasant stuttering", with the fix that "A remainder of dt/2 means that we are currently halfway between the current physics step and the next" so the remainder is used "to perform a linear interpolation between the two physics states". The clamp `frameTime > 0.25` and the spiral-of-death discussion are part of the same canonical text.

**What it buys, precisely, for this loop:** it does not touch the render interval at all. The render call in the loop above is unconditional and unthrottled — the pattern changes *which simulation time is on screen*, removing the staircase that appears when `dt` is not commensurate with the frame interval. In a VSync-locked loop whose p50 is already one panel period, the accumulator cannot reduce the p50, because the loop is not choosing when to present: the presentation engine is (A1). Its value here is content-time correctness (and, for the record, the app's current design of fixed `sim::DT = 1/60` stepped up to a per-frame `SIM_BUDGET` is a *bounded-catch-up* variant, i.e. a semi-fixed scheme, without the interpolated render state).

**A3. [PRIMARY] Engine-owned variants, so the pattern's variants are not folklore.**

- Unity: "The fixed update loop simulates code running at fixed time intervals but in practice the interval between fixed updates isn't fixed. This is because a fixed update always needs a frame to run in and the duration of a frame and the length of the fixed time step are not in perfect sync. If a fixed time step completes during the current frame, the associated fixed update can't run until the next frame." (Unity Manual, *Fixed updates*.) Unity's render-side entry point is `Update`, and its physics interpolation is exposed as `Rigidbody.interpolation`.
- Godot: the pattern is a first-class engine feature named *fixed timestep interpolation*; the interpolated transform is computed from a previous and current tick with the "physics interpolation fraction", retrieved per frame via `Engine.get_physics_interpolation_fraction()` ("Returns the fraction through the current physics tick we are at the time of rendering the frame. This can be used to implement fixed timestep interpolation."). Godot's documentation also owns the cost analytically: "If we are interpolating between the current and previous ticks, we are not estimating the position of the object _now_, we are estimating the position of the object in the past. To be exact, we are estimating the position of the object _between 1 and 2 ticks_ into the past." and "The most significant effect is there can be a slight delay to input". (Godot 4.4 docs, *Introduction* — Physics Interpolation.)
- Unreal Engine: frame pacing is defined as the opposite of uncapped rendering: "**Frame Pacing** is a system that restricts an application to rendering frames at a lower framerate than a device's native refresh rate. This enables the application to prioritize consistency and stability in rendering, providing for a smoother user experience compared with letting the framerate run uncapped." (Epic, *Frame Pacing for Mobile Devices in Unreal Engine*.) Engine knobs: `FrameRateLock`, `r.setframepace`, `FPlatformRHIFramePacer::SetFramePace`, plus "Smooth Frame Rate" / "Use Fixed Frame Rate" project settings.

**A4. [PRIMARY] Sleeping to a cadence on macOS: what the APIs guarantee, and what Apple says about their accuracy.**

- Rust `std::thread::sleep`: "Puts the current thread to sleep for **at least** the specified amount of time. The thread may sleep longer than the duration specified due to scheduling specifics or platform-dependent functionality. **It will never sleep less.**" and "On Unix platforms, the underlying syscall may be interrupted by a spurious wakeup or signal handler. To ensure the sleep occurs for at least the specified duration, this function may invoke that system call multiple times." (Rust std docs, `std::thread::sleep`.) The distribution of overshoot is one-sided by contract — which is exactly the shape that biases a *median* late.
- What that maps to on macOS: Rust's Apple implementation of `fn sleep_until` calls `mach_wait_until(deadline)`, with the source comment "Make sure to round up to ensure that we definitely sleep until after the deadline has elapsed" and the note that the function's only public documentation is Apple TN2169 (`library/std/src/sys/thread/unix.rs`, `#[cfg(target_vendor = "apple")] pub fn sleep_until`).
- Apple's own guidance on that API, TN2169 *High Precision Timers in iOS / OS X*: "At the time this note was written, mach_wait_until() is the api we would recommend using. It has the lowest overhead of all the timing API that we measured." The same note owns the accuracy expectation: "if an otherwise unloaded machine or device is consistently missing your scheduled time by more than **500 microseconds**, that should be considered an error, please file a bug with Apple. Often times we can do much better than that, but its best to measure for yourself." And it owns the scheduling precondition: "The only difference between a regular timer and a high precision timer is the scheduling class of the thread making the timer request. Threads that are in the real time scheduling class get first class treatment. They go to the front of the line whenever they need to run." — with the code to enter that class via `thread_policy_set(..., THREAD_TIME_CONSTRAINT_POLICY, ...)`. It also warns: "Don't spin loop!" and "Don't create large numbers of real time threads."
- The kernel side of the same call, XNU `osfmk/kern/clock.c`: `mach_wait_until_trap` blocks with `assert_wait_deadline_with_leeway((event_t)mach_wait_until_trap, THREAD_ABORTSAFE, TIMEOUT_URGENCY_USER_NORMAL, deadline, 0)` — leeway 0 — and the leeway machinery is on a separate path, `_clock_delay_until_deadline_with_leeway`, whose comment reads "For now, assume a leeway request of 0 means the client does not want a leeway value." So `mach_wait_until` does **not** silently coalesce: it asks for a strict deadline. Coalescing is opt-in elsewhere and is documented as such: `DispatchSourceTimer.schedule(deadline:repeating:leeway:)`, "`leeway` — The maximum amount of time after `deadline` by which the system may delay the delivery of the timer event. … The system may defer the deliver of timer events to improve power consumption and system performance."
- The structural weakness of any sleep-based limiter is stated by Apple in the pacing context (see A5): a timer can be *out of phase* with the display, and no sleep API on macOS takes a vsync time as its reference.

**A5. [PRIMARY] Display-link-driven loops: what the timestamps mean, and what Apple recommends them for.**

- `CADisplayLink` is available on macOS 14.0+ (`API_AVAILABLE(macos(14.0))` in `QuartzCore/CADisplayLink.h`) and on macOS is created from a view/screen/window: `NSView.displayLink(target:selector:)` — "Returns a new display link whose callback will be invoked in-sync with the display the view is on." (Apple docs; header: "For macOS, see NSView/NSWindow/NSScreen.displayLink(withTarget:selector:)."). The header owns the timestamp semantics: `timestamp` is "The current time, and duration of the display frame associated with the most recent target invocation", and `targetTimestamp` is "The next timestamp that the client should target their render for." Apple's reference page states it as: "The time interval that represents when the next frame displays", with the usage guidance "You can use the target timestamp to cancel or pause long running processes that may overrun the available time between frames in order to maintain a consistent frame rate." The recommended per-frame budget is computed as `targetTimestamp - timestamp` (Apple, `CADisplayLink.duration` discussion: "You calculate the expected amount of time your app has to render each frame by using targetTimestamp-timestamp. Use targetTimestamp-CACurrentMediaTime() to calculate the actual amount of time.").
- Apple's explanation of *why* a display link beats a timer for this purpose, WWDC21 10147: "CADisplayLink wakes up at every vsync and invokes the callback. This provides the application the entire 8ms to complete its work." and "A regular timer, such as an NSTimer, is very unlikely to be in perfect sync with the display. It can be out of phase or drifting, so sometimes the app may not have enough time to complete its work and it leads to frame drops." The same session names the best practices for a custom render loop driven this way: query the refresh rate at runtime rather than hard-coding it; "use the actual frame rate of the CADisplayLink"; "Use targetTimestamp to ensure a hitch-free frame rate transition"; and compute the time delta dynamically from `previousTargetTimestamp` because "callbacks may be skipped entirely", in which case "the time delta that you should use is not 8ms, but rather 16ms".
- `CVDisplayLink` (legacy) is deprecated: the whole API block in `CoreVideo.framework/Headers/CVDisplayLink.h` sits inside `API_DEPRECATED_BEGIN("use NSView.displayLink(target:selector:), NSWindow.displayLink(target:selector:), or NSScreen.displayLink(target:selector:) ", macos(10.4, 15.0))`. Its callback receives `const CVTimeStamp *inNow, const CVTimeStamp *inOutputTime` (`CVTimeStamp` fields: `videoTime`, `hostTime`, `rateScalar`, `videoRefreshPeriod`, …; `CoreVideo/CVBase.h`) — note there is **no** `targetTimestamp` field in `CVTimeStamp`; the "target" naming exists only on `CADisplayLink`/`CAMetalDisplayLink`.
- `CAMetalDisplayLink` (macOS 14.0+, `QuartzCore/CAMetalDisplayLink.h`) is the Metal-specific variant: `CAMetalDisplayLinkUpdate` carries `drawable`, `targetTimestamp` and `targetPresentationTimestamp`; the class doc says it is "a specialized way to interact with variable-rate displays when you need more control over the timing window to render your app's frames", that "The system makes a best effort to make callbacks at appropriate times", and that for less visually intensive apps `CADisplayLink` is the right tool. Its only pacing knob, `preferredFrameLatency`, is coarse: "The only acceptable values are `1.0` and `2.0`." with the caveat "The final latency may be bigger if the system needs more time, such as for windowed modes on macOS."

**A6. [PRIMARY] The blocked-present loop: what it is actually waiting on, and what wgpu 25 can and cannot reach.**

- wgpu 25, `PresentMode::Fifo`: "Calls to `Surface::get_current_texture()` will block until there is a spot in the queue." (`Surface::get_current_texture` — "Returns the next texture to be presented by the swapchain for drawing.")
- On Metal that block is `CAMetalLayer.nextDrawable()`: "Waits until a Metal drawable is available, and then returns it. … If all drawables are in use, the layer waits up to one second for one to become available, after which it returns `nil`." (Apple docs.) In this configuration the one-second escape hatch is disabled: wgpu-hal 25 calls `setAllowsNextDrawableTimeout:false` during `configure` (`if caps.can_set_next_drawable_timeout { let () = msg_send![*render_layer, setAllowsNextDrawableTimeout:false]; }`, `wgpu-hal/src/metal/surface.rs`), so `nextDrawable` waits indefinitely for a drawable rather than returning `nil`. The number of drawables comes from the app's surface config: wgpu-hal 25 `wgpu-hal/src/metal/surface.rs`, `fn configure`: `render_layer.set_maximum_drawable_count(config.maximum_frame_latency as u64 + 1);` with `maximum_frame_latency` = `desired_maximum_frame_latency` = 2 for this app, and Apple documents that value as settable to "`2` or `3` only; if you pass a different value, Core Animation ignores the value and throws an exception. The default value is `3`."
- Present is a plain drawable present; the pacing variants are **not** used. wgpu-hal 25 `wgpu-hal/src/metal/mod.rs`, `SurfaceTexture::present`: `if !texture.present_with_transaction { command_buffer.present_drawable(&texture.drawable); } command_buffer.commit();`. Apple's frame-pacing present calls are `presentDrawable:afterMinimumDuration:` and `presentDrawable:atTime:` (WWDC21 10147 lists them under "Drawable present APIs with frame-pacing" versus plain `presentDrawable:` "Drawable present API without frame-pacing"), and wgpu 25 exposes neither.
- Present mode coverage on Metal in wgpu 25 is only two modes: `let display_sync = match config.present_mode { wgt::PresentMode::Fifo => true, wgt::PresentMode::Immediate => false, m => unreachable!("Unsupported present mode: {m:?}") };` then `setDisplaySyncEnabled: display_sync` (`wgpu-hal/src/metal/surface.rs`, v25.0.0). `displaySyncEnabled` is documented as "A Boolean value that determines whether the layer synchronizes its updates to the display's refresh rate. … If `false`, the layer presents new content more quickly, but possibly with brief visual artifacts (*screen tearing*). The default value is `true`."
- Apple's assessment of exactly this design — a loop paced by drawable back-pressure — is explicit and negative on fixed-rate displays. WWDC21 10147, describing the snippet `nextDrawable` → encode → plain `presentDrawable:`: "We're relying on the back pressure of a Drawable being available to set our frame rate for us. On a fixed-rate display, we know that this isn't the best idea, since there's no guarantee that your GPU work will align to the refresh rate of the display." Apple's recommended alternative for pacing on a fixed-rate display in the same session: if "your app's GPU work consistently exceeds the display's on-glass interval, we've previously recommended that you slow down your rendering to hit the next factor of the display's fastest refresh rate. Typically, that means lowering your target frames per second to 30 from 60". On Adaptive-Sync (variable-rate) displays Apple changes that guidance to "attempt to present frames at the highest rate your app can do so evenly" — and Adaptive-Sync requires a supported Mac, a VRR display, and "your app needs to be running in full-screen mode", detected via `NSScreen.minimumRefreshInterval != maximumRefreshInterval` plus `NSFullScreenWindowMask`. None of that applies to a fixed 60 Hz built-in panel.

**A7. [PRIMARY] Where the loop's cadence actually comes from in winit 0.30 on macOS.**

Reading the vendored winit **0.30.13** — the version `Cargo.lock` pins (checksum `a6755fa58a9f8350bd1e472d4c3fcc25f824ec358933bba33306d0b63df5978d`), source at `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/winit-0.30.13/` — `src/platform_impl/macos/app_state.rs`: the `pending_redraw: RefCell<Vec<WindowId>>` queue (:42) is filled by `queue_redraw` (:297-303 — `pending_redraw.push(window_id)` :300, `self.ivars().run_loop.wakeup()` :302) and drained in `fn cleared(&self, panic_info: Weak<PanicInfo>)` (:369), whose comment reads "Called by RunLoopObserver before waiting for new events" (:368): `let redraw = mem::take(&mut *self.ivars().pending_redraw.borrow_mut());` (:384), then `WindowEvent::RedrawRequested` per queued window (:386-390), then `Event::AboutToWait` (:392). A second emission site exists through AppKit drawing: `src/platform_impl/macos/view.rs` implements `#[method(drawRect:)] fn draw_rect` (:202-203) and calls `self.ivars().app_delegate.handle_redraw(window.id())` (:208) into `app_state.rs` `handle_redraw` (:277-284). The code is identical in structure to what was first read at the v0.30.5 tag; every citation in this file is now against 0.30.13. So on macOS the redraw event is delivered by the CFRunLoop observer immediately before the loop goes back to waiting: there is no vsync alignment anywhere in the mechanism, and the only thing that can slow the loop down is the work inside the redraw handler — which, with Fifo, is dominated by the blocking `nextDrawable()` in A6. This matches winit's own documentation of the API: `Window::request_redraw` "Queues a `WindowEvent::RedrawRequested` event to be emitted that aligns with the windowing system drawing loop. … However as the event aligns with the windowing system drawing loop, it may not arrive in same or even next event loop iteration." The platform-specific list in that doc names alignment behaviour for Windows (`WM_PAINT`), Wayland (frame callbacks) and Web (`requestAnimationFrame`) — none is claimed for macOS. winit is also explicit, at 0.30.13, that `AboutToWait` itself is not the right hook for drawing: "Emitted when the event loop is about to block and wait for new events. … High frequency event sources, such as input devices could potentially lead to lots of wake ups and also lots of corresponding `AboutToWait` events. This is not an ideal event to drive application rendering from and instead applications should render in response to [`WindowEvent::RedrawRequested`] events." (`src/application.rs`:110-121.) The redraw that a hook like this requests still executes inside `RedrawRequested`, which is where winit expects the drawing to happen. A separate winit issue tracks the macOS redraw semantics as a bug: "Fundamentally, drawing inside `kCFRunLoopBeforeWaiting` is just plain incorrect." (rust-windowing/winit#2640, opened by a winit maintainer, still open, updated 2026-06-20.)

**A8. [PRIMARY] A first-party vsync source does not exist in winit 0.30, and that is a known, open design gap.**

rust-windowing/winit#2412 *Implement VSync source (frame pacing)* (opened 2022-08-08, open, updated 2026-03-18) proposes `WindowEvent::Frame` plus `Window::request_frame()`, and states the per-platform APIs it would use: "X11 - Xpresent / macOS - `DisplayLink` / Wayland - frame callbacks / Windows - DWM get composition timings + a timer. / Web - request animation frame." Neither proposal exists in the pinned 0.30.13: scanning the vendored crate for `request_frame`, `WindowEvent::Frame` and `FrameThrottled` matches only an internal Wayland helper (`src/platform_impl/linux/wayland/window/state.rs:253 pub fn request_frame_callback`), so there is no public API to ask winit for a vsync-throttled redraw. A maintainer comment in the same issue states the macOS situation plainly: "On macOS / iOS it looks like the recommended way to throttle rendering is via a `CADisplayLink /CVDisplayLink` callback which abstracts away from synchronizing with any compositor, but should approximately throttle to the vsync." The issue also records the structural difference between the two families of pacing mechanism: "In both cases though the synchronization (or I'd say throttling for a composited environment) comes _after_ you have rendered something and submitted it to be presented." — i.e. blocked present is retrospective, a display link is predictive. (Maintainer statements; tagged as practice in Part B.)

### Part B — Shipped practice (independent [ANECDOTE] reports)

These are reports about *practice*: what shipping projects did, observed and worked around. They are not used above as the authority for any mechanism; where a mechanism claim appears in them, the mechanism authority is the Part A source.

**B1. [ANECDOTE] Dolphin (Metal backend, shipped emulator) on `presentDrawable:` as an involuntary frame limiter.** `Source/Core/VideoBackends/Metal/MTLGfx.mm`: "PresentDrawable refuses to allow Dolphin to present faster than the display's refresh rate when windowed (or fullscreen with vsync enabled, but that's more understandable). … It also seems to improve frame pacing, so enable it by default with vsync" — the code path selects `presentDrawable:` when vsync is active and otherwise defers `[drawable present]` to a scheduled handler. Independent confirmation, from a shipping app, that the blocked drawable path is what caps the loop and that it was judged better for frame pacing than presenting freely.

**B2. [ANECDOTE] Ebiten (Go game engine) pins the drawable count to 3 on macOS.** `internal/graphicsdriver/metal/view_darwin.go`: "maximumDrawableCount is the maximum number of drawable objects. Always use 3 for macOS (#2880, #2883, #3278). At least, this should work with MacBook Pro 2020 (Intel) and MacBook Pro 2023 (M3)." The same engine's CoreAnimation shim notes the hard limit and the failure mode: "It can set to 2 or 3 only. SetMaximumDrawableCount panics for other values." (`internal/graphicsdriver/metal/ca/ca_darwin.go`.)

**B3. [ANECDOTE] egui/egui-wgpu ships a macOS-specific drawable-count workaround for AppKit live resize.** `crates/egui-wgpu/src/winit.rs`: "Transaction presentation can hold a drawable during AppKit live resize. Keep the configured low-latency path normally, but use three Metal drawables while resizing." — i.e. the effective frame-queue depth is treated as a runtime variable, not a constant, and the resize path is where the blocked-present loop misbehaves.

**B4. [ANECDOTE] Neovide (winit-based Rust app) documents macOS vsync stutter and the workaround it shipped.** neovide/neovide#2093, opened by a maintainer: "On some macOS systems the frame rate stutters a bit due to a buggy vsync implementation. If you have that issu, it's recommended to: 1. Start Neovide with the command `--no-vsync` to disable the vsync and switch to a software based timer. 2. Set `g:neovide_refresh_rate` … to the same as your current monitor refresh rate." The same thread records a Tracy capture of the blocked-present loop: "It draws two frames quickly, then waits for almost 30 ms, before drawing two frames again. It looks like it should be doing 60 FPS, since it allows that many frames to be rendered." The issue points at winit#2412 (A8) as the real fix, and the project later implemented a macOS frame-callback vsync source of its own.

**B5. [ANECDOTE] Tristan Hume, `CVDisplayLink` phase measurements (2017, with a public correction).** The post's own summary: "`CVDisplayLink` just fetches the refresh rate of your display, and sets a high resolution timer to call you every 16.6ms (for a 60hz display)." His disassembly-based experiment initially showed the callback landing at arbitrary phases run-to-run; the correction is the important part for practice: "The `MTKView` I was testing with uses `CVDisplayLinkCreateWithActiveCGDisplays` which if you have multiple displays creates a `CVDisplayLink` 'capable of being used with all active displays', i.e it doesn't use vsync. … I re-did my experiments in Instruments on my laptop display and found that it consistently fired the `draw` call half-way into the frame, about 7ms from the next vsync." So: single-display `CVDisplayLink` is phase-stable (roughly mid-frame, ~7 ms of lead on a 60 Hz panel), multi-display creation degrades to a plain timer. This is a measurement, not a mechanism authority; the mechanism authority for callback timing is A5.

**B6. [ANECDOTE] JetBrains Skiko ties inflight CPU frames to the drawable count.** `skiko/src/awtMain/objectiveC/macos/MetalRedrawer.mm`: `/// max inflight command buffers count matches swapchain size to avoid overcommitment` followed by `device.inflightSemaphore = dispatch_semaphore_create(device.layer.maximumDrawableCount);` — a shipping toolkit treating `maximumDrawableCount` as the concurrency budget of the whole frame pipeline.

**B7. [ANECDOTE] Blur Busters / jorimt, *G-SYNC 101* — the measured limiter-versus-VSync study.** The series' structure is an input-lag test programme on a 240 Hz display (§ 3 "Input Lag & Test Methodology", § 11 "In-game vs. External FPS Limiters", § 14 "Optimal G-SYNC Settings & Conclusion"). It is the standard measured reference for what a frame limiter does to pacing in the presence of V-SYNC, and it is the origin of the widely repeated "cap a few frames below refresh" practice. It is included as measured practice, not as a mechanism source; the normative version of "restrict the app below the panel rate" that a first party publishes is Epic's (A3) and AMD's auto-tune, which for fixed-refresh displays "will match the peak refresh rate. For example: 60 FPS on a 60Hz display" (AMD, *How to Configure Radeon Chill and Radeon Anti-Lag*, DH-033). NVIDIA's equivalent KB article ("Max Frame Rate: Cap Frame Rates, Save Power, and More", nvidia.custhelp.com answer 4958) could not be verified: direct fetch returned HTTP 403 on 2026-09-12, so no quote from it is used here.

**B8. [ANECDOTE] Godot and Filament ship the "present with a target duration/time" pacing calls, reachable by native code.** Godot's Metal driver calls `presentDrawableAfterMinimumDuration(drawable, present_minimum_duration)` whenever `vsync_mode != VSYNC_DISABLED` and plain `presentDrawable` when vsync is off (`drivers/metal/rendering_context_driver_metal.cpp`); Google Filament selects `presentDrawable:atTime:` when a presentation time is supplied and otherwise plain `presentDrawable:` (`filament/backend/src/metal/MetalHandles.mm`). Both are evidence that the API family Apple recommends in A6 exists and is used in production — and, by contrast, that wgpu 25 does not call it.

## Options for NeuroArena

Ranked by expected effect on the p50 interval of this loop, on a fixed 60.00 Hz panel. "Can it reach p50 ≤ 16.667 ms?" is answered against the constraint from A1: the display consumes at most one frame per period, so the best attainable median is the period itself; no option can produce a median *below* one period, and any option that adds phase uncertainty can only move the median further from it.

**O1. Keep `PresentMode::Fifo`, but stop using the blocked present as the loop's clock: take the frame-start time from a display link.**
- Mechanism: the loop currently starts each frame when `nextDrawable()` unblocks, i.e. at an arbitrary point *after* a vsync. A display link delivers a callback at a known point *before* the next vsync together with the target time of the frame it is asking for (A5), which makes the frame start deterministic relative to the panel rather than a consequence of when the previous frame's drawable freed up (A7).
- Exact APIs: `NSView.displayLink(target:selector:)` → `CADisplayLink` with `targetTimestamp` (macOS 14.0+), or `CAMetalDisplayLink` if the app owns the `CAMetalLayer` directly; the existing `request_redraw`-in-`about_to_wait` driver (winit 0.30) must be replaced by something that runs on that callback.
- Preconditions: (i) macOS 14+ for `CADisplayLink`/`CAMetalDisplayLink` (macOS 15+ if the legacy `CVDisplayLink` route were used instead, which is deprecated — do not); (ii) winit 0.30 exposes no frame/throttle event (A8), so this requires reaching the view/window below winit (`raw-window-handle`) or using the layer directly; (iii) the app crate declares `unsafe_code = "forbid"` (`app/Cargo.toml`), so raw Objective-C messaging must live behind a safe dependency API or a scoped lint exemption; (iv) the redraw must complete before `targetTimestamp`; (v) run-loop mode integration (`add(to:forMode:)`) is required.
- Expected effect on the p50 interval: removes the "frame starts an arbitrary amount after the vblank" component and makes the interval distribution center on exactly one period; it changes *variance and phase*, not the lower bound.
- Cost: another callback source to keep coherent with winit's event loop; a skipped callback must be handled by delta-from-previous-target rather than a nominal interval (A5); no tearing; power cost is lower or equal (no extra frames); portability is macOS-only unless kept behind a trait.
- Reaches p50 ≤ 16.667 ms? It is the only option that acts on the quantity the measurement shows (the median sits +12.3 µs off the period at x100 and −8.7 µs at x0). It can center the median on the period; it cannot push the median below the period, and it cannot guarantee the sign of the residual.

**O2. Add fixed-timestep render interpolation (canonical accumulator, A2/Godot variant).**
- Mechanism: keep `sim::DT` fixed; store previous and current simulation state; render `previous*(1-alpha) + current*alpha` with `alpha = accumulator / DT`.
- Exact APIs/constants: none (application data structure); Godot's equivalent reference API is `Engine.get_physics_interpolation_fraction()`; the canonical formulation is A2's code.
- Preconditions: the render path must be able to sample two simulation states per entity; the app must accept rendering content that is between 1 and 2 ticks in the past (Godot, A3).
- Expected effect on the p50 interval: **none.** The accumulator does not choose when to present; with Fifo the interval is set by the display (A1) and the loop's phase (O1). Its effect is on apparent motion smoothness when the tick rate is not commensurate with the frame rate.
- Cost: one tick of additional content/input delay (Godot: "between 1 and 2 ticks into the past", "slight delay to input"); extra state copies per frame; no power or tearing change; fully portable.
- Reaches p50 ≤ 16.667 ms? No, not by itself.

**O3. Uncapped render (`PresentMode::Immediate`) plus an application-side limiter.**
- Mechanism: `displaySyncEnabled = false` on the layer (wgpu 25 maps `Immediate` to it, A6), with pacing supplied by the app: `mach_wait_until` on a deadline derived from `mach_absolute_time`, or a `DispatchSourceTimer` with `leeway` set explicitly.
- Preconditions: `Immediate` is reported in `SurfaceCapabilities::present_modes`; the app must own its own deadline arithmetic and phase correction; if the window is windowed (this app is), the macOS compositor still composites at the panel rate (A1, A5), so the freedom gained is in *submission* time, not in *display* time.
- Expected effect on the p50 interval: worse or equal. Apple's mechanism statement is that a timer without a display reference is "very unlikely to be in perfect sync with the display. It can be out of phase or drifting… it leads to frame drops" (A5). A limiter at exactly the panel period will drift against the panel by construction; a limiter slightly below it removes the drift problem only by abandoning period-locked presentation.
- Cost: tearing where the compositor permits it (in windowed mode the compositor may still hold the frame, so the tearing may not even be the payoff — B4 records the same doubt), plus added latency if the limiter blocks after the vsync boundary, plus an entire second clock to debug; `mach_wait_until` is not the problem here — the phase reference is.
- Reaches p50 ≤ 16.667 ms? No. This is a latency tool (AMD describes its own anti-lag feature exactly this way: "helps reduce input-to-response latency ('input lag') by reducing the time passed between the game's sampling of user controls and the output appearing on display"), not a median-interval tool.

**O4. Cap the render rate *below* the panel rate (the "limiter" school, B7).**
- Mechanism: pick a target strictly below 60 fps so that every frame trivially meets its deadline; on a fixed-rate panel the effective display cadence becomes a multiple of the panel period, and the loop's own submissions stop racing the vsync boundary.
- Exact API/constant: application-side pacing (O3's machinery) or, in engine terms, Unreal's `r.setframepace` / `FPlatformRHIFramePacer::SetFramePace` (A3).
- Expected effect on the p50 interval: strictly worse than the current loop (p50 becomes ~2 panel periods for a 30 fps target). Its documented purpose is consistency and stability, not a lower median (Epic, A3).
- Cost: halves the delivered frame rate; reduces power; portable.
- Reaches p50 ≤ 16.667 ms? No — it targets the opposite direction. Relevant here only as the escape hatch Apple itself recommends when GPU work exceeds the on-glass interval (A6), which the measurements say is not this app's situation (draw+present is dominated by the blocking present itself, not by GPU work).

**O5. Use Metal's frame-pacing present calls (`presentDrawable:atTime:` / `afterMinimumDuration:`).**
- Mechanism: instead of `present` immediately, hand Metal an explicit target presentation time or a minimum frame duration, so the presentation engine itself schedules the drawable (Apple: these are the "Drawable present APIs with frame-pacing", A6; WWDC21 uses exactly `afterMinimumDuration:` to hit a chosen 78 Hz cadence).
- Exact API/constant: `-[MTLCommandBuffer presentDrawable:atTime:]`, `-[MTLCommandBuffer presentDrawable:afterMinimumDuration:]`. Apple demonstrates both on macOS in WWDC21 10147; an exact minimum-OS availability for `afterMinimumDuration:` could not be verified from an Apple-owned header in this investigation (third-party bridge headers annotate it `macos(10.15.4)`, unverified), so treat availability as needing a check against the Metal headers on the deployment target.
- Preconditions: a Metal-level presentation path. **Not reachable from wgpu 25**: `wgpu-hal` 25's Metal `SurfaceTexture::present` calls only `present_drawable` + `commit` (A6), and `PresentMode` has no variant that selects a paced present. Reaching this requires native Metal code or an upstream wgpu change.
- Expected effect on the p50 interval: this is Apple's own recommended mechanism for even pacing on both fixed-rate and Adaptive-Sync displays; it can hold a cadence but cannot beat one period on a fixed-rate panel.
- Cost: a parallel non-wgpu rendering path (large); no tearing; macOS-only.
- Reaches p50 ≤ 16.667 ms? Bounded by A1; whether it is *better* than O1 for this loop is unmeasurable without implementing both.

**O6. Do nothing to the loop; reduce per-frame work so the frame cannot miss its slot.**
- Mechanism: A1 says a missed slot costs a full period; the measurements show `sim` at 0.123 ms (x100) and `draw+present` at 16.4–16.5 ms, i.e. the frame's own duration is dominated by waiting, not by work. Reducing work therefore cannot change the median, only the tail (p99 was 17.3–18.4 ms; max 40.2 ms at x100 — the tail is where the missed slots are).
- Expected effect on the p50 interval: none.
- Cost: none.
- Reaches p50 ≤ 16.667 ms? No; it is a tail-latency measure, worth doing for its own reasons and separately measurable.

**What the measurements plus A1/A7 imply about the 12 µs question.** `[INFERENCE]` The current loop is a back-pressure-paced loop (A6, A7): every frame starts when the previous frame's drawable is released, which is after a vblank, plus whatever the run-loop observer and the scheduler add. A median interval of 16.679 ms at x100 is 12.3 µs above one period, while at x0 the median is 8.7 µs *below* it: the distribution straddles the period and its median is set by where the wake-ups land, not by an algorithmic error in the loop. Apple's own published accuracy budget for high-precision timers is 500 µs (A4) — 40× the gap in question — so a fix should be expected to change the *shape* of the loop's phase (O1) rather than to buy 12 µs from any single API.

## What does not work

1. **`PresentMode::Mailbox` on Metal — does not exist in wgpu 25.** wgpu 25's Metal surface configure panics for any mode other than `Fifo` and `Immediate`: `m => unreachable!("Unsupported present mode: {m:?}")` (`wgpu-hal/src/metal/surface.rs`, v25.0.0). wgpu's own docs agree: Mailbox is "Supported on: DX12 on Windows 10, NVidia on Vulkan and Wayland on Vulkan." The same applies to `FifoRelaxed` — "Supported on: AMD on Vulkan."
2. **`Immediate` as a route to a *tighter* median on macOS.** `Immediate` maps to `displaySyncEnabled = false`, whose documented behaviour is "the layer presents new content more quickly, but possibly with brief visual artifacts (*screen tearing*)" — a change in cadence discipline, not in interval. In windowed mode the compositor still presents on the panel cadence (A1/A5), so the expected result is the same median with worse regularity.
3. **A plain timer as a pacing source.** Apple: "A regular timer, such as an NSTimer, is very unlikely to be in perfect sync with the display. It can be out of phase or drifting, so sometimes the app may not have enough time to complete its work and it leads to frame drops." (WWDC21 10147.) `mach_wait_until` is a *strict* wait (leeway 0, XNU `mach_wait_until_trap`), which makes it reliable but not vsync-referenced; `DispatchSourceTimer` leeway is explicitly a permission to be late ("The maximum amount of time after `deadline` by which the system may delay the delivery of the timer event").
4. **Trying to schedule sub-period precision with the OS timer stack.** Apple's own error budget for "high precision timers" is: "if an otherwise unloaded machine or device is consistently missing your scheduled time by more than 500 microseconds, that should be considered an error" (TN2169). Rust's cross-platform contract makes the overshoot one-sided by design — "It will never sleep less" — so a sleep-based deadline cannot be used to *pull a median earlier*.
5. **Spin-waiting to shave the last microseconds.** Apple, same note: "Don't spin loop! This burns cpu and battery at very high rates, and when newer faster hardware is released you'll burn cpu and battery even faster!" and, for the real-time class that would otherwise be needed: "Don't create large numbers of real time threads. Real time scheduling isn't magic… If everyone tries to crowd to the front of the line, all the real time threads will fail."
6. **`CAMetalDisplayLink.preferredFrameLatency` as a fine-grained knob.** "The only acceptable values are `1.0` and `2.0`." (Apple docs.) There is no sub-frame latency target to tune.
7. **`desired_maximum_frame_latency = 1` as a "tighter pacing" fix.** It only shrinks the drawable pool: wgpu-hal sets `maximumDrawableCount = latency + 1`, Apple allows only 2 or 3, so `1` means a 2-drawable pool. Shipped practice treats that as risky: egui's low-latency config carries the comment "`Some(1)` cuts FPS in half" for iOS (`crates/egui-wgpu/src/lib.rs`), and wgpu's own field documentation warns for larger values that "⚠️ On 60hz displays the latency can be very noticeable."
8. **Expecting winit 0.30 to hand the loop a vsync-aligned event.** There is no such event (A7 code path, A8 open issue: `request_frame`/`WindowEvent::Frame` are proposals, not shipped API as of the issue's 2026-03-18 update), and the macOS redraw is dispatched from the run-loop observer immediately before the loop blocks. Any display-link strategy must therefore bypass or extend winit.
9. **`CVDisplayLink` as the modern answer.** Deprecated in macOS 15.0 with a stated replacement (`NSView`/`NSWindow`/`NSScreen.displayLink(target:selector:)`), and its callback's `CVTimeStamp` has no `targetTimestamp` field, so it cannot express "the time the next frame will be displayed" the way `CADisplayLink` does.
10. **Assuming a fixed-refresh panel can be made to present more often.** Adaptive-Sync scheduling requires a VRR-capable display, a supported Mac, and full-screen operation (`NSScreen.minimumRefreshInterval != maximumRefreshInterval` distinguishes the modes, per WWDC21 10147). On the author's fixed 60 Hz panel, `minimumRefreshInterval == maximumRefreshInterval`, so the entire Adaptive-Sync branch of Apple's guidance — including "present frames at the highest rate your app can do so evenly" — does not apply.

## Report back

- The measurable target is a *phase* problem, not a throughput problem: one panel period is 16.6667 ms and the measured p50s (16.658 / 16.679 / 16.664 ms) bracket it within ±13 µs, while Apple's own published accuracy budget for its high-precision timer API (`mach_wait_until`, TN2169) is 500 µs. Nothing in the loop's own work distribution explains the residual — `sim` is 0.001–1.579 ms and `draw+present` is dominated by the blocking present.
- The loop's cadence has one author: the swapchain back-pressure. wgpu 25's Fifo blocks `get_current_texture` → Metal `nextDrawable()` (drawable count = `desired_maximum_frame_latency + 1` = 3), and on macOS winit 0.30 delivers `RedrawRequested`/`AboutToWait` from the CFRunLoop observer with no vsync alignment at all. Apple explicitly calls this design "not the best idea" on fixed-rate displays (WWDC21 10147).
- The only application-level lever on that median is making the frame *start* at a known point before a known vsync instead of after the previous present unblocks: a display-link-driven loop (`NSView.displayLink` → `CADisplayLink.targetTimestamp` on macOS 14+, or `CAMetalDisplayLink`). It cannot push the median below one period; it removes the ±12 µs of phase wander.
- Everything else is the wrong tool: interpolation (Gaffer/Godot) changes content time, not frame interval and costs 1–2 ticks of delay; uncapped `Immediate` + a timer limiter is a *latency* tool whose pacing source Apple describes as "out of phase or drifting"; capping below the panel rate (Unreal frame pacing, AMD auto-tune) makes the median worse by design.
- Grounded negatives worth recording: Mailbox and FifoRelaxed do not exist on Metal in wgpu 25 (the match arm is `unreachable!`); Metal's frame-pacing present calls (`presentDrawable:atTime:`/`afterMinimumDuration:`, shipped by Godot and Filament) are not reachable through wgpu 25; `CVDisplayLink` is deprecated in macOS 15 with no `targetTimestamp`; `preferredFrameLatency` accepts only 1.0 or 2.0; winit has no frame-throttling event (issue #2412 still open) and `desired_maximum_frame_latency = 1` is shipped-practice-risky rather than a pacing fix.
